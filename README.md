# Запрет (EXP) — Android-версия стратегии `general (EXP).bat`

Одно приложение с одним тумблером, которое делает на телефоне то же, что на ПК делает
`bin\winws.exe` из папки `zapret-discord-youtube-1.10.4` (проект
[Flowseal/zapret-discord-youtube](https://github.com/Flowseal/zapret-discord-youtube),
движок — [bol-van/zapret](https://github.com/bol-van/zapret)) по кнопке
`general (EXP).bat`: десинхронизирует DPI, чтобы YouTube и Discord перестали тормозить.

Готовый файл: **`app/dist/Zapret-EXP.apk`** (≈60 КБ, `ru.zapret.exp`, подпись v1+v2,
minSdk 24 / targetSdk 34, только arm64-совместимый DEX — ставится на любой Android 7+).

Никакого шифрования и чужих серверов: туннель локальный (`VpnService`), трафик уходит
напролом к тем же адресам, что и без приложения. Меняются только способ отправки и
количество «видимых» инспекции пакетов.

## Сборка — без Gradle, без NDK, без сети

Нужны только JDK 17, Android SDK (platform 34 + build-tools 34) и Python 3 (для
перешивки `classes.dex` в APK):

```bash
cp local.env.example local.env      # пути к JDK/SDK, staging и ключу подписи
bash run_tests.sh                   # 101 проверка ядра и конфига на обычной JVM
bash run_relay_test.sh              # 21 проверка TCP-ретранслятора: 300 КБ эхо и настоящий TLS
bash app/build.sh Zapret-EXP        # aapt2 compile/link -> javac -> d8 -> zipalign -> apksigner
```

`app/build.sh` использует штатные утилиты SDK; ни один шаг не лезет в интернет.
`local.env` (реальные пути твоей машины и пароль ключа) в git не попадает.

`run_relay_test.sh` поднимает стенд: синтетический TCP-клиент <-> `TcpFlow` <-> реальный
сервер. Сначала локальное эхо на 300 КБ (байт в байт, по порядку), потом настоящий TLS
handshake с разрезанным ClientHello. Проверяются вещи, которые по отдельным функциям не
видны: номера последовательности, окна, контрольные суммы каждого пакета, отсутствие RST
и отсутствие шторма взаимных ACK.

Ключ подписи создаётся один раз и не должен теряться — без него обновление APK не
встанет поверх установленного:

```bash
keytool -genkeypair -v -keystore keys/my.keystore -alias my \
        -keyalg RSA -keysize 2048 -validity 10000
KEY=keys/my.keystore KSAlias=my KSPass='пароль' bash app/build.sh Zapret-EXP
```

## Кнопка «Проверить, работает ли в моей сети»

На экране, под тумблером. Отвечает на главный вопрос без догадок и без логов:
для `youtube.com`, `discord.com` и `github.com` (контроль) она делает **две** попытки
подряд — обычный TLS и тот же ClientHello, но разрезанный приёмами из правил
(фрагментация + фейки, как в `general (EXP).bat`). Собственный трафик приложения
исключён из туннеля, поэтому замеряется ровно то, что увидит инспекция провайдера.
В конце — блок `ИТОГ`, например:

```
youtube.com: БЕЗ десинха блокируется, С десинхом проходит — стратегия работает
discord.com: не проходит ни так, ни так (timeout / timeout) — блокировка не этого типа
github.com: проходит и так, и с десинхом — блокировки нет
```

Если «не проходит ни так, ни так» — причина не в приложении: в этой сети нужен другой
приём (другое число точек, другой TTL, `quic-block` вместо QUIC или отказ от фейков).
Это и есть способ понять, будет ли работать, не гадая по три раза на установку APK.

## Установка и проверка на телефоне

1. Взять `Zapret-EXP.apk` (из релиза репозитория или скопировать файлом) и установить.
2. Открыть «Запрет (EXP)», включить тумблер. Система спросит разрешение на постоянное
   VPN-соединение — согласиться (там же можно включить «Использовать всегда», тогда
   туннель поднимется сам после перезагрузки).
3. Внизу — журнал. Он должен показывать именно работу стратегии, а не тишину:
   ```
   TCP -> 142.250.90.4:443 (www.googlevideo.com) установлен
   десинк [google-youtube] tls 142.250.90.4:443 фрагменты=[1, 3, 5] + фейк ttl=8
   udp-fake [quic-general] x11 ttl=8 -> 162.159.135.234:443
   ```
   Счётчики сверху: потоки TCP/UDP, сколько раз применён десинк (TLS / HTTP / QUIC),
   объём трафика.
4. Проверить видео YouTube и голосовой/видеозвонок в Discord. Выключить тумблер — всё
   работает как без приложения.

Если не работает — сначала журнал: по строкам «десинк …» видно, применяется ли стратегия
вообще. Тогда крутят параметры правил (см. ниже), а не весь код сразу.

**Если тумблер включился и сам отжался** — экран теперь обязан показать причину
(строка «Причина отказа: …» и последние строки журнала). Варианты, что обычно мешает на
оболочках вроде HiOS/MIUI:
* системный экран разрешения закрыт без согласия → открой тумблер ещё раз;
* «Постоянная VPN-служба» (`Настройки → Безопасность и приватность → VPN → Постоянная
  VPN-служба`) занята другим приложением → сними её и повтори;
* оболочка убила сервис в фоне → в `Настройки → Приложения → Запрет (EXP) → Батарея`
  выбери «Без ограничений» (и разреши автозапуск);
* тип foreground-сервиса или конфигурация туннеля не приняты системой — в этом случае
  приложение само перебирает варианты туннеля (v4+v6+свой DNS → v4+v6 → только v4) и
  пишет в журнал, какой сработал.
Сообщение «Причина отказа» + журнал — это ровно то, что нужно для точной правки.

## Как перенесена стратегия

| Блок `general (EXP).bat` | Что делает приложение |
|---|---|
| 1. QUIC-fake, `repeats=11`, `quic_initial_www_google_com.bin`, list-general | правило `quic-general`: UDP 443/8443 по адресам из списков → 11 фейковых QUIC Initial с TTL 8, байты берутся из того же `.bin` |
| 2. Discord UDP 19294-19344 / 50000-50100, `repeats=4` | правило `discord-udp`: те же порты, 4 фейка из `ACTIVE_DISCORD_UDP.bin` |
| 3. `discord.media`, TCP 2053/2083/2087/2096/8443, fake+multisplit `repeats=8` | правило `discord-cdn`: фрагментация ClientHello по 8 точкам + разделение заголовка TLS-записи |
| 4. YouTube, `--dpi-desync=hostfakesplit`, `mod=host=www.google.com` | правило `google-youtube`: фрагментация + фейк с подменой SNI на `www.google.com` |
| 5. Основной list-general, TCP 80/443, fake+multisplit `repeats=4` | правило `general-main`: фрагментация по 4 точкам + фейк из `tls_clienthello_www_sferum_ru.bin` |
| 6-9. блоки по `ipset-all.txt` | в папке zapret `ipset-all.txt` содержит одну заглушку, поэтому на ПК эти блоки не обрабатывают ничего. Здесь вместо них правила `quic-any` / `quic-block` (выключены, раскомментируются при необходимости) |

Полное соответствие и обоснование замен: [`docs/exp-strategy.md`](docs/exp-strategy.md).

Чем Android без root отличается от WinDivert: нельзя менять номер последовательности,
TCP Timestamp и вставлять байты в чужой поток. Поэтому:

* **TCP** — только сохраняющие поток приёмы: фрагментация (несколько `write()` с
  `TCP_NODELAY`, позиции из `split=`) и разделение заголовка TLS-записи. Фейковый
  ClientHello уходит **отдельным соединением с малым TTL**, а не врезается в поток —
  иначе сервер получил бы мусор вместо handshake.
* **QUIC/UDP** — приём перенесён точно: датаграммы независимы, поэтому дополнительные
  фейковые Initial с TTL 8 работают как на ПК.
* `--dpi-desync-fooling=ts` → малый TTL фейка (пакет видит инспекция, сервер — нет).

## Что можно крутить без переписывания кода

`app/assets/rules-exp.txt` (пересборка — секунды):

```
general-main|tcp|80,443|zapret-general,zapret-google|fake=tls_clienthello_www_sferum_ru.bin,split=1:4:1,ttl=8
```

* `ttl` фейка: 8 → 5 → 2;
* `split=1:4:1` → `1:8:1` (больше точек) или `1:2:1`;
* `mss=200` — заставить ядро дробить запрос ещё мельче;
* `# quic-any|udp|443|*|...` — фейки по всем UDP:443 (было в блоках 6-9);
* `# quic-block|udp|443|*|drop=1` — отбрасывать QUIC, чтобы приложения ушли на TCP+TLS,
  где включена фрагментация;
* домены — в `app/assets/pc/zapret-general.txt`, `zapret-google.txt`, `discordmedia.txt`,
  исключения — `zapret-exclude.txt`. Синтаксис списков совпадает с `lists/` из папки zapret
  (`^домен` = только сам домен, `домен` = домен и поддомены).

## Скорость: на что смотреть, если интернет «стал медленнее»

Туннель добавляет к каждому соединению пользовательскую терминацию, поэтому скорость —
это отдельная задача, а не побочный эффект. Что сделано:

| Приём | Эффект |
|---|---|
| window scaling (RFC 7323) в обе стороны: своё объявляем `wscale=4` (~1 МБ), окно клиента умножаем на его scale из SYN | без этого потолок — 65535 байт на круг задержки, примерно 1 МБ/с на LTE |
| MTU туннеля подбирается под реальный линк (`MTU линка − 60`, 1280…1400) | на LTE с MTU 1420 сегменты в 1400 байт фрагментировались и терялись — «видео то тормозит, то нет» |
| кэш DNS-ответов (2 минуты, 200 записей, ID подставляется) | резолв больше не добавляет полный круг к каждому новому соединению; в счётчиках видно «DNS: из кэша N» |
| фейковые TCP-соединения уходят в фоновую очередь | +1 RTT на handshake с каждого нового соединения исчез |
| явный таймаут подключения 8 с вместо ~2 минут | мёртвый адрес не вешает поток, приложение получает RST сразу |
| повторный SYN на переиспользованный порт = новое соединение (раньше попадал в «терпение» старого потока и терялся) | убирает «RST от клиента» и зависшие коннекты |
| запрос читается пачками до 12 MSS, а не по одному сегменту | меньше системных вызовов на путь |

Если нужно ещё быстрее/медленнее — в правилах: `mss=NNN` (резать ответы сервера мельче,
это может помочь против DPI, который собирает сегменты, но слегка режет скорость),
уменьшение `repeat` у QUIC-фейков, отключение лишних правил.

## Ограничения rootless-VPN

1. Групповые адреса (224.0.0.0/4, ff00::/12) и broadcast не релелятся: с включённым
   тумблером mDNS/Chromecast и «устройства в локальной сети» могут не находиться.
2. Каждое TCP-соединение терминалируется в пользовательском пространстве. Отдача клиенту
   идёт строго в пределах объявленного им окна (с учётом window scaling), при закрытом
   окне поток ждёт 45 с и закрывается (в журнале — «клиент не открыл окно»).
3. DNS-серверы не подменяются: запросы идут туда же, куда слала система — как zapret на ПК.
4. **IPv6.** Туннель с маршрутом `::/0` на сети без IPv6-канала — ловушка: приложение
   видит AAAA, «IPv6 же есть», подключается в никуда и получает «нет связи». Поэтому
   приложение проверяет линк (`IPv6 вверх: есть/нет` в журнале) и, если канала нет,
   поднимает туннель только для v4 и убирает AAAA из DNS-ответов. Если IPv6 вверх есть —
   ничего не меняется, v6 работает как обычно.
5. Лимиты: до 512 TCP- и 400 UDP-потоков, 1 МБ буфер вверх, 8 МБ вниз.

## Проверено автоматикой (`run_tests.sh` — 101, `run_relay_test.sh` — 21)

* разбор и сборка IPv4/IPv6 + TCP/UDP, контрольные суммы, round-trip данных;
* SNI из реальных fake-паттернов папки zapret, подмена SNI при совпадении длины;
* HTTP Host, DNS: разбор A/AAAA по настоящему ANCOUNT (смещение 6, а не 8), имена со
  сжатием 0xC0, уборка AAAA из ответа с пересчётом ANCOUNT, ключ вопроса для кэша;
* инвариант «фрагментация не теряет и не дублирует байты» для длин 1…1500;
* арифметика окна TCP, включая переходы через 32-битную границу номера последовательности
  и масштабированные окна (65535 << scale);
* TCP-опции: чтение window scaling из SYN, сборка SYN с MSS+scale, данные при этом
  не сдвигаются;
* весь конфиг, лежащий в APK: 5 правил, наличие всех fake-файлов, разбор параметров,
  совпадения правил для `discord.com`, `www.googlevideo.com`, `twitch.tv`, `discord.media`,
  UDP 19300, порты и параметры, перенесённые из bat.

Не проверено на живом телефоне в конкретной сети — для этого нужен сам телефон:
APK ставится вручную, а журнал приложения показывает, применялась ли стратегия.
